# Full Practical Ministry Research

Use `full-discipleship-practical-research-cycle` to investigate church methods from question through verified practical learning and publication. It can complete without choosing a local program or designing a pilot.

| Request | Owner | Main product |
|---|---|---|
| Does a method produce an outcome? | full-discipleship-research-cycle | Assessed evidence/findings |
| How do ministries do this? Run the full practical research cycle. | full-discipleship-practical-research-cycle | Verified methods, comparison, Practice Cards, report |
| What should Southbrook implement? | full-discipleship-practice-design-cycle | Local fit, action warrant, proposed test |
| Evaluate these actual exercises; create our tool. | full-discipleship-resource-equipping-cycle | Resource reviews, original draft tools |
| Build an entire course. | full-discipleship-curriculum-build-cycle | Capability progression and session assets |
| Teach me this supplied book without new research. | Source distillation when available | Attributed learning brief |

Explicit source, no-save, format and routing choices override defaults. When a full research request explicitly emphasizes practical church methods or less empirical research, select the practical cycle before the generic research route. Do not force an empirical literature review into a descriptive question.

## Complete sequence
1. Retrieve existing relevant practice learning and sources; avoid duplicate investigation/cards.
2. Bound the practical question and source contract.
3. Investigate original operational materials; preserve raw report/register/ledger.
4. Reopen originals using `discipleship-practice-source-verifier`.
5. Compare implementation and capture useful practices with exact locators.
6. Update the right knowledge layer only where learning warrants it.
7. Publish the requested report, verify authorized filing/indexing, give plain-language learning and stop.

## Verification appropriate to the claim
A manual can establish what it instructs. A firsthand account can establish reported use. Observation/records are needed for observed enactment. Outcomes and causal interpretations require their own support. Keep these separate from how completely a method is described and from whether Southbrook should try it.

Record unknown operational details. Do not invent a coaching rhythm or infer that one is absent merely because the reviewed source omits it. Disclose historical/current version uncertainty, source-family dependence, failure-case access and rights boundaries.

Research confidence can remain limited while a method is useful to understand. Neither repeated adoption nor a polished resource proves effectiveness. Preserve theological reasoning and human ministry judgment separately.

## Useful report
Lead with methods, operational examples, comparison and tradeoffs. Include roles, steps, cadence, materials, modeling, attempted practice, feedback, readiness, oversight, support when struggling, burden, limits and source access. Label original illustrations. Place technical registers and evidence checks after readable learning.

Default a requested full report to PDF plus editable master; honor requested formats. Distinguish raw, corrected, verified, draft, proposed and adopted. A complete bounded comparison can leave Living Synthesis unchanged and recommend no pilot.

## Preservation and portability
Reuse existing Practice Intelligence destinations; do not create another Brain layer. Resolve all destination names/IDs live. Avoid speculative numbered folder assignments, including the resource workflow's proposed sibling. Preserve raw report, corrections, source register and final outputs with linked IDs. Verify writes and report blockers honestly.

Refresh a resume checkpoint after major stages. A later run reads the checkpoint and confirmed files before continuing; it does not duplicate writes. Never imply automatic continuation or field results.

Install the orchestrator and source verifier with their bundled references. Companions can be loaded from their verified installed locations or the canonical repository. Missing companions require a disclosed bounded fallback, not invented execution.
