# Southbrook document builds

Dan's standing direction, 2026-10-23: apply Southbrook Church branding to every authored document created for him in this project, including internal Brain records and native Google Docs. This shared production layer applies across all skills; individual skills do not need to repeat it. The manager verifies the final result.

## Shared flow

`requested content → Southbrook brand + relevant document pattern → requested-format production → content/layout/brand QA → authorized save + read-back → verified link`

1. Keep the content-owning skill responsible for purpose, sources, interpretation, audience, and status.
2. Read [the brand skill](../skills/southbrook-brand-artifact-stylist/SKILL.md), its brand profile, and the relevant [observed document patterns](../skills/southbrook-brand-artifact-stylist/references/document-patterns.md). Verify the current Drive reference/assets for substantial production. Reuse this packet within a batch rather than repeatedly fetching unchanged sources.
3. Choose a layout suited to the artifact: compact learning note, practical handout, working agenda, workbook, or long report. Apply the main Southbrook Church identity, not a generic template or an unrelated ministry sub-brand.
4. Create in the requested format. Native Google Docs require real typography/color/heading changes and the verified logo where suitable; plain default styles are insufficient. Requested DOCX/PDF, slides, and spreadsheets use their own production tools. Do not create extra formats merely to demonstrate branding. For deliberately plain Markdown/text, use clear hierarchy and identity/provenance where the format supports it; do not claim unsupported visual styling.
5. Complete the format-specific QA and the brand skill's checks. For PDFs/DOCX and paginated Google Docs with image/page-fit requirements, render and inspect. Check headings, table breaks, source links, readable contrast, logo proportions, page numbers, and visible status. For native-only records without page-fit requirements, read back content and actual styles. Report any unverified visual result honestly.
6. Save only within existing authorization, verify the parent and final body, and deliver the verified link. A request to build a document does not itself authorize public publication or sending it to people.

## Coverage

| Workflow output | Brand application |
|---|---|
| Practical learning packs, indexes, internal summaries | Compact identity header, clear title/sections, restrained cyan accents, source/coverage notes |
| Curriculum, leader/participant guides, handouts | Recognizable header, practical section sequence, modeled example, room to practice, clear next step |
| Research publication | Southbrook palette/sans-serif hierarchy; retain the report's evidence-weighted answer, citations, confidence, and source appendix |
| Agendas, decisions, capture records | Compact identity; readable headings; owners/actions where relevant; preserve exact quotes and status |
| Requested slides/screens/spreadsheets | Same church identity adapted to the medium; retain functional meaning and accessibility |

Existing source PDFs, uploaded evidence, third-party books, and original notes are not restyled or relabeled as Southbrook-authored sources. A new branded summary remains a derived document with clear attribution. Code/config files and chat answers do not require additional graphic files. Explicit later user direction overrides the default.

## Backlog work

A request to change future workflows does not itself start a backlog restyle. When a batch is authorized, inventory the actual saved IDs, distinguish our documents from original sources, preserve links/content/approval, restyle in place where possible, and checkpoint each verified result. Do not create a second full learning library just to change the design.

## Scope of enforcement

These are assistant operating instructions followed by sessions loading this repository, not a model-running GitHub Action or an account-wide setting. Future producers must apply the shared layer even if their specialist instructions omit a separate brand step. A change on a PR branch remains pending on the default branch until merged.
